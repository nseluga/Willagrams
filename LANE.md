## Global rules

- **Tests.** Run each package serially on an idle machine, never while `xcodebuild` is running (a parallel run produced 22+ spurious timeouts):
  `swift test` (rules 53) · `swift test --package-path Tests/BoardTests` (271, XCTest — its swift-testing runner reports "0 tests", read the XCTest "Executed N tests" line instead) · `Tests/MatchTests` (128) · `Tests/StyleTests` (44) · `Tests/ShellTests` (291, `--no-parallel`) · `Tests/SettingsTests` (37) · `Tests/BotTests` (68, ~7 min) · `Tests/OnlineTests` (168, 1 known pre-existing issue at `WholeMatchScript.swift:98`, live cases skip without a key) · `Tests/AudioTests` (19) · `Tests/AccountTests` (21) · `Tests/FriendsTests` (54).
  **These counts are floors.** A count may only go up. Never delete a passing test to hold a number; a test pinning behaviour this round changes is rewritten to the new rule, not deleted.
- **Always run ShellTests as `swift test --package-path Tests/ShellTests --no-parallel`.** Its cases are `@MainActor` and poll at 1ms, so running them concurrently starves them against their own 10s deadlines — the same tree gave 12 issues in parallel and 4 serially. Item 5 fixed those 4, and items 6, 7, 8 and 9 added to it, so the suite is now **291 with 0 issues**: any red is yours. Never read the collected count as the result — round 2 did, and recorded a failing suite as green.
- **A background test run in a SHARED worktree is timestamped, not pinned.** Item 4's agent queued a ShellTests run behind a wait-for-idle loop; it finished at 05:20 and came back green at 276, and the agent concluded its earlier "four standing failures" report had been machine load all along. It was not. Items 5, 6 and 7 all committed into that same worktree between the queue and the finish (03:06, 04:12, 05:13), so the run executed against a tree where item 5 had already fixed the four — including the genuine retain cycle, mutation-proven as a signal-6 crash. Two of the four were assertions pinning behaviour the app no longer has, which no amount of load can turn green. Before reading any long-running background result, compare its finish time against `git log` for the worktree it ran in. Open question for the shutdown suite: a parallel run collects 276 where `--no-parallel` collects 271 — reconcile that count before recording a final number.
- **A whole-declaration contiguous literal pins TEXT, not REACHABILITY — state the path invariant up front.** Item 7 burned two attempts and item 8 burned three on the same family, one level higher each time: a literal covering a declaration leaves free both the predicates that declaration branches on and every enclosing view above it. The invariant that closes it, and the one to hand a builder on the FIRST attempt of any "a user reaches X" item, is: *every declaration AND every predicate on the path from `ShellRootView`'s route arm down to the action call is either inside one contiguous literal or asserted by value.* Require the builder to walk that path link by link and enumerate the coverage in its report; do not let it patch only the mutations QA named. Two asymmetries to carry: a `private` predicate (`TwoPlayerView.isHost`) takes no value pin from the test target, so a literal is its only possible cover; and `ShellRootView.swift` is excluded from the ShellTests target, so pin it by reading source off disk with `OrientationTests.rootViewWiring`'s existing reader rather than writing a second one. Budget 3+ attempts for any `ui: true` item of this shape — in both items the production code was correct on attempt 1 and every attempt went into the pin. **Item 9 confirmed this rule pays for itself: it is the first item this round to land its reachability pin on attempt 1, and the only difference was that this invariant was in the builder's prompt from the start rather than discovered by three rounds of QA.** So state it up front, always — the cost is one paragraph, the saving is two attempts. Live for item 11.
- **When two pieces of state suppress the same UI, clearing one leaves it suppressed.** Item 9's review caught this as a real user-visible bug: `sendInvite` cleared `lobby.declinedBy`, but `canBanner` independently refused any matchID still in `bannered`, so re-inviting a friend who had just declined showed them nothing for up to the 120s `inviteLifetime`. Both flags had to be cleared; clearing the one the feature was "about" was not enough. Whenever an item adds a second reason to hide, dismiss, disable or debounce something, enumerate every existing gate on that same UI and decide each one explicitly — and pin the RE-entry case, not just the first entry, because the first entry passes either way. Live for items 10 and 11, where a waiting state, an ended state and a reconnect grace will all gate the same board.
- **A mutation battery and a gate run in the same worktree are not independent.** Item 8 reported BLOCKED on gate runs that were red from its OWN concurrently-running battery rewriting the sources underneath the test process — not from the pin. The same interleaving made a transient read of a mid-battery tree look exactly like a committed bug (an inverted `if !friends.isEmpty` arm that was really the battery's mutation in flight), and made one real mutation print 0 because a restore raced the gate. Before reading ANY gate result or diagnosing ANY source, quiesce the tree: confirm a stable mtime and a clean `git diff` against HEAD. Never interleave a restore with a running battery, and re-run in isolation any mutation whose batch result disagrees with its neighbours before recording it as a hole. **The precise mechanism, worth knowing because it is silent:** a source-scan pin reads the view file off disk at test-EXECUTION time, not at compile time, so a `cp`-restore that lands after the run is launched but before the test reads the file makes the mutation invisible and scores 0 — indistinguishable from a vacuous pin, and it costs an attempt chasing a phantom. So shasum-verify that the mutation is STILL ON DISK at the moment the run starts, not only after it ends, and treat any 0 as unproven until reproduced in isolation. **Corollary, and the reason this rule is now three paragraphs long: an ungated diff left in the tree at hand-back may be a mutation that was never restored, not work in progress.** Item 9 handed back with uncommitted changes across three files; two hunks were legitimate test scaffolding, but the third silently deleted the guest-side `isAcceptedFriend` guard — which is mutation MQ2 from that item's own battery, and a direct breach of its "a decline must not reach a stranger" guardrail. Gating that diff would have shipped the breach. So never gate a hand-back's leftover diff on the assumption it is unfinished work: read every hunk against the item's own mutation list and guardrails first, and when any hunk is a mutation, discard the whole diff back to the item's green commit (`cp` from `git show <sha>:<path>`, never `git checkout --`) and carry the unfinished coverage as documented debt. A green, QA-passed, review-clean commit stands on its own; ungated work on top of it does not inherit any of that.
- **A row the backend hands back is written to `ShellModel.currentProfile`, or it is a stale-row bug.** `currentProfile` is the app's one profile source of truth. Item 6 found two callers discarding a returned row: `ProfileModel.save()` (the saved name never reached the shell) and `MatchOutcomeRecorder.swift:263` (Played / Won / Tiles placed / Fastest win frozen at sign-in). Any new backend call returning a profile row writes it back, and its test asserts `shell.currentProfile` changed — not the screen's own copy, which is exactly the assertion that shipped this bug green in round 2.
- **A fix that adds an async refresh can make the test that proves the fix vacuous.** Item 6 attempt 2's new `showProfile()` re-read raced ahead of the assertions and supplied the answer, so deleting the production write-back left the whole suite green where attempt 1 had gone red on three behavioural issues. - **`guard let self` before an `await` is a STRONG capture.** `[weak self]` on the closure alone does not bound a suspended task's lifetime — item 6's builder asserted it did and QA disproved it by experiment. Bind what the suspension needs before the `await`, rebind self after.
- **A "the view renders X" pin is ONE contiguous match against normalized source, never several independent `contains`.** ShellTests excludes the view files, so a source scan is the only headless pin available — and independent substring checks prove the strings exist in the file, not that a user reaches them unconditionally. Normalize the whole file (trim each line, drop `//` lines, join with `\n`), then match a single literal spanning the anchor line, the call, and the block's closing brace — the technique `OrientationTests.rootViewWiring` already uses. Gate the attempt on a mutation that makes the call **unreachable**, not merely absent. The price is brittleness: adding a legitimate sibling view next to a pinned call false-reds the test, and you extend the literal. That is the correct price. Live for items 8, 9, 11 and 13.

- **An off-executor callback is a `nonisolated` function, not an inline closure.** Any callback UIKit or a backend SDK may invoke on its own executor — `requestGeometryUpdate(errorHandler:)`, realtime `onWire`/`onPresence`, a scene-phase or reachability handler — is a `nonisolated static func` on a plain policy or adapter type, passed by reference. A closure written inline inside a SwiftUI view or any other `@MainActor` context silently inherits that isolation and traps in `dispatch_assert_queue` the first time it is called off the main queue. This is exactly what item 1 fixed; items 9 and 10 touch the same class of callback.
- **A launch that does not crash is weak evidence.** Item 1's QA rebuilt the pre-fix commit and launched it clean on the same iPad, because the handler only fires on a timeout that does not reproduce on demand. So an isolation fix is proven by a compile-time pin — a real call from a non-isolated context in a test — and by the removed frame matching the crash frame, not by a green launch. Run the launch anyway; just never treat it as the proof.
